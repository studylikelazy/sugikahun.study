## 2. 本書の前提と補完範囲

発注時点で提示されたのは **「1. プロジェクト基本概要」** と **「2. ゲームの二大柱とコア・ゲームプレイループ」の冒頭** までである。
それ以降（世界観設定の詳細、コアシステムの個別指定）は受領できていないため、本書では以下の方針で設計側が補完した。

1. 提示済みの要素（タイトル、ジャンル、視点／アートスタイル、コア・フィロソフィー、昼夜二分構造、
   「巨大シャッターを開けるとそのまま首都高の合流レーンへ出る」シームレス拠点）は **確定仕様として不可侵** に扱う。
2. 未受領の領域は、確定仕様から論理的に導かれる案を提示し、節見出しに `【補完】` を付す。
3. 差し替えが起きやすい箇所（固有名詞、年代、キャラクター、価格、プラットフォーム）は
   `08_data_schema_and_balance.md` の **データ定義側に外出し** し、文章を書き換えずに差し替えられる構造にした。

## 3. 設計判断ログ（Key Design Decisions）

後から「なぜこうなっているか」を失わないための記録。変更時はこの表に追記する。

| # | 判断 | 理由 | 却下した代替案 |
|---|---|---|---|
| D-01 | 工場の生産物は **車ではなく「実験データ（DATA）」と「1点物の部品」** | コア・フィロソフィーの直訳。量産販売を主目的にすると Factorio の劣化版になり、JDM文脈も死ぬ | 完成車を量産して販売する経営SLG（既存プロト `KOBO Motorworks` の方向） |
| D-02 | **公差（Tolerance）と歩留まり** を品質系の中心に据える | 「同じ部品でも精度が性能になる」というエンジニアリングの核。Factorioの「品質」とは異なり、**計測・補正・工具摩耗のフィードバックループ**という自動化パズルになる | 単純な星付きレア度 |
| D-03 | 敵・戦闘の代わりに **三種の圧力**（近隣圧／取締り圧／資金圧）を置く | 攻撃してくる敵がいないと拡張が無制限になり緊張が消える。日本の都市部工場＋走り屋という設定に最も自然な「反作用」 | 産業スパイ、暴力団、災害のみ |
| D-04 | 夜パートの主目的は **金ではなくテレメトリ（D5データ）** | 走ること自体が研究の必須入力になり、二大柱が一方通行でなく相互依存になる | 夜＝資金稼ぎ（工場が育つと夜に行く理由が消える） |
| D-05 | 進行ゲートは **筑波TC2000のラップタイム** | 「速さ」という一次元の明快な指標。あらゆるシステムの出力がここに合流する | 売上高、名声ポイント |
| D-06 | シミュレーションは **20Hz 固定ステップ・完全決定論** | リプレイ、ゴースト、ベンチマーク、セーブ互換、バグ再現のすべてがこれに依存する | 可変Δtの逐次更新 |
| D-07 | 工場は 2Dドット（クォータービュー）、走行は疑似3D。**3Dの統一は行わない** | 発注の確定仕様。加えて、2台の描画系を分ける方が少人数で到達可能な画質上限が高い | 全編3D |
| D-08 | 実在の自動車メーカー名・車種名は使わず **架空マルク（fictional marque）** で統一 | ライセンス交渉を前提にすると制作が止まる。文化的記号（直6ツインターボ、2ローター、4G系4WD等）は **構造として** 再現すれば伝わる | 実名ライセンス取得 |
| D-09 | 地名（首都高、C1、筑波）は **実在名を使いつつ、路線形状は再構成** | 固有名詞は作品の訴求の核。ただし測量再現はせず「記憶の中の形」に再構成し、権利・安全面の注意書きを添える（`09` §5） | 完全架空地名／完全実測再現 |
| D-10 | 放置進行（オフライン生産）は **資源のみ、研究は不可** | 工場を見に行く理由を残す。研究＝データ変換はプレイヤーの設計判断の結果であるべき | 完全放置可 |
| D-11 | ラップタイムは **走行シム本体ではなく準定常ソルバ** でも算出可能にする | セットアップ比較を「走らずに」評価できると、工場パートに設計の意味が生まれる（＝シミュレーション棟の価値） | 常に実走のみ |
| D-12 | Web技術（TS/WebGL2）で実装し、デスクトップ版は Tauri でラップ | 既存リポジトリ資産（Vite + React + TS + Cloudflare Pages/GH Pages）を継承でき、Web体験版という強力な集客導線が持てる | Unity / Godot / 独自C++ |
| D-14 | パーツとベース車の入手は **4つの市場**（カタログ／ヤード／オークション／コネクション）に分け、**乱数の軸を市場ごとに分離**する | ランダム性を1本の太いダイヤルにすると体験が「運の良い日／悪い日」に潰れる。4分割すれば「どの乱数を引き受けるか」がプレイヤーの戦略になる。さらに乱数は決定論シード＋床＋天井＋鑑定（＝情報を買うと分散が縮む）で囲い、**S/BP等級は市場に流さない**ことで工場の存在意義を守る（`10` §8） | 単一の「ガチャ商店」／完全固定価格のショップ（どちらも選択が消える）／海外並行輸入を加えた5市場（薄まるため見送り） |
| D-13 | 章ゲートのタイムは **先に決めず、準定常ソルバの実行結果から決めた**（`shared/midnight/lap-solver.ts`） | 当初案（1:05 / 1:00 / 0:57 / 0:54 / 0:51）を実装して解いたところ**物理的に到達不能**と判明した。コース全長を公称 2,045 m に合わせ、走行ライン係数を実在の最速記録（非フォーミュラ 49秒445）に合わせて較正したうえで、各Actの想定スペックが**ゲートを 0.2〜0.8 秒だけ下回る**ように数値を置き直した。結果として最終到達点 Act6 は理論 0:49.486／推定 0:49.833 となり、**48秒台には届かない**＝現実の最速クラスに並ぶところが天井になる | 体感と雰囲気でタイムを置き、実装時に辻褄を合わせる（＝ゲートが到達不能／逆にヌルくなる事故が確定する） |

## 4. 用語集（Glossary）

| 用語 | 定義 |
|---|---|
| **TICK** | シミュレーションの最小時間単位。1 tick = 50 ms（20 tick/s）。工場・経済・時間経過はすべて tick で駆動する |
| **ゲーム日（GD）** | ゲーム内の1日。`昼フェーズ`＋`夜フェーズ`で構成。既定で実時間 約14分（`01` §6） |
| **HERO CAR** | プレイヤーが最終的に1台だけ仕上げる主役車両。全システムの出力が集約される |
| **DATA（D1〜D6）** | 研究の投入資源。Factorio のサイエンスパック相当だが、**物理的な試験の副産物**として生成される（`05` §3） |
| **公差 / Tolerance** | 部品の設計寸法からの許容誤差。`±0.100 mm` 〜 `±0.003 mm` の7段階 |
| **等級 / Grade** | 公差判定の結果（`C` / `B` / `A` / `S` / `BP`）。`BP` は選別・摺り合わせ済みのブループリント品 |
| **歩留まり / Yield** | 投入数に対する目標等級到達数の比率 |
| **工程能力 Cpk** | 工程の安定度指標。機械の等級分布を決める内部値（`02` §9） |
| **近隣圧 / NUISANCE** | 騒音・排気・排水・振動により蓄積する行政＆近隣からの圧力（0–100） |
| **取締り圧 / HEAT** | 夜間走行で蓄積する警察側の警戒度（0–100）。覆面・検問・オービスの出現率を支配する |
| **SPゲージ** | 夜のローリングバトルにおける気力／集中の残量。相手との距離差で減少する |
| **テレメトリ・パケット** | 夜間走行で取得する生ログ。解析ラボで D5 に変換される |
| **ライン** | 工場の1本の生産系統。`ラインレート[個/分]` が主要KPI |
| **デマンド** | 30分単位の平均電力ピーク。契約電力を超えると遮断＋違約金（`02` §7） |
| **準定常ソルバ** | コースを区間分割し、各区間の限界速度から理論ラップを解く計算器（`03` §9） |
| **BP品** | Blueprint（ブループリンティング＝実測選別・摺り合わせ）を通した最上級部品 |
| **Attack / アタック** | 筑波でのタイムアタックセッション。1セッション20分、タイヤ1セットが基本 |

## 5. 既存リポジトリとの関係

本リポジトリ（`studylikelazy/sugikahun.study`）には、現在 `client/src/pages/Home.tsx` に
**KOBO Motorworks（日本全国マップ＋6機械の簡易オートメーション）** の実装が存在する。
本企画はその上位互換であり、以下の資産を継承する。

| 既存資産 | 本企画での扱い |
|---|---|
| Vite + React 19 + TS + Tailwind + shadcn/ui | **継承**。HUD／管理画面系UIはそのまま使う |
| `tick` ベースの `advanceGame()` | **思想を継承**し、Worker上の決定論シミュレータへ発展（`07` §3） |
| localStorage セーブ（`kobo-nippon-motor-grid-v1`） | **IndexedDB + バイナリ**へ移行。旧セーブは読み捨て（互換不要と判断） |
| `@babylonjs/core` の背景3Dシーン | **原則不使用**。ガレージ閲覧モードのみ任意採用（`07` §6.4、バンドル肥大のリスクあり） |
| Cloudflare Pages / GitHub Pages デプロイ | **継承**。Web体験版の配信経路（`07` §11） |

移行計画は `07_tech_spec.md` §12 に Phase 0〜4 として記載。

## 7. 実行可能な参照実装（`shared/midnight/`）

本バンドルは「読むだけの設計書」で終わらせないため、**数値根拠となる部分を実コードで同梱**している。
いずれも外部依存ゼロ・`tsc --strict` を通る純粋 TypeScript で、ブラウザ／Node／Worker のどこでも動く。

| ファイル | 内容 | 対応する章 |
|---|---|---|
| [`shared/midnight/types.ts`](../../shared/midnight/types.ts) | 車両・部品・コース・公差等級・研究の**型定義と定数**（`GRADE_TOLERANCE_MM`、`GRADE_QUALITY_FACTOR`、難易度補正など）。ランタイムコードを持たない「契約」 | `08` §1 |
| [`shared/midnight/tsukuba.ts`](../../shared/midnight/tsukuba.ts) | 筑波TC2000 のコースデータ（**16区間・合計 2,045 m ちょうど**、半径／勾配／縁石可否／セクター分割） | `05` §1.2、`08` §6 |
| [`shared/midnight/lap-solver.ts`](../../shared/midnight/lap-solver.ts) | 準定常ラップソルバ本体。`solveLap(track, spec, conditions)` が理論ラップ・推定ベスト・セクタータイム・速度トレース・**区間別の限界要因**を返す | `03` §9 |
| [`shared/midnight/market.ts`](../../shared/midnight/market.ts) | 4市場の在庫生成・相場指数・鑑定・二位価格オークション・解体・**入札エージェント**。すべて `hash32(saveSeed, 市場, 週)` からの決定論生成 | `10` 全体 |
| [`shared/midnight/market.test.ts`](../../shared/midnight/market.test.ts) | Vitest 回帰テスト 34件。`10` §8 の「ランダム性の7原則」をそのまま検査項目にしたもの | `10` §8 |
| [`shared/midnight/lap-solver.test.ts`](../../shared/midnight/lap-solver.test.ts) | Vitest 回帰テスト 22件。コース全長の整合、全Actのゲート到達性、単調性、**感度の符号**、μ寄与 > パワー寄与×3、雨／冬／燃料、決定論、セクタ合計、アップシフト回数、最高速レンジ、1・2ヘアがトラクション限界であること | `08` §7 |

```bash
pnpm add -D vitest                   # 本リポジトリには未導入（lockfile を更新すること）
pnpm vitest run shared/midnight      # 回帰テスト：56 passed（ソルバ22＋市場34）
```

> テストは **バランス表の守り手**である。`08` §7 の数値を変えたらテストが落ちる、
> コース区間長を変えたら全長チェックが落ちる——という形で、設計書とコードの乖離を機械的に止める。
> （`shared/midnight/*.test.ts` は `tsconfig.json` のビルド対象外なので、本体ビルドには影響しない。）

## 8. 変更管理

- 本バンドルの数値（バランス値）は `08_data_schema_and_balance.md` の表を **単一の正** とする。他ドキュメントの数値は引用。
- 仕様変更は「判断ログ（§3）への追記」＋「該当ドキュメントの改訂」をセットで行う。
- ドキュメント内の `【補完】` `【要検証】` `【P2】`（優先度2＝1.0以降）のタグは実装前に必ず棚卸しする。
